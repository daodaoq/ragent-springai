## P0 — 直接影响正确性 / 安全性 / 稳定性

### P0-1 幻觉防线薄弱

- [x] 1a. 检索无相关性阈值：低相关 chunk 照常进 prompt；空结果仍触发生成。→ **已修**：`ragent.retrieval.min-score`（默认 0.3，仅 rerank 成功路径生效）+ `ragStream` 空召回硬门禁直接返回提示语、不再调生成模型（`RetrievalServiceImpl.retrieve`、`RagServiceImpl.ragStream`）
- [x] 1b. 引用 `[N]` 无校验：模型可编造超出文档数的编号。→ **已修**：prompt 显式给出 `[1]~[N]` 可引用范围 + 系统提示词禁止编造编号 + 生成后 `validateCitations` 越界告警留痕（`RagServiceImpl`）
- [x] 1c. 实体误抽 filename 致零召回且不降级：硬过滤让双路全空，空结果不重试。→ **已修**：实体过滤下零召回自动去掉 filter 重试一次（`RetrievalServiceImpl.retrieve`）
- [x] 1d. 提示词注入：文档 / 历史原样拼 prompt，无边界符与"不可信数据"声明。→ **已修**：`buildPrompt` 每条来源加 `【来源 N】…【/来源 N】` 分界符 + 系统提示词声明知识库内容为不可信数据、忽略其中指令；`StructuredExtractor` 同步加固（`RagServiceImpl`、`StructuredExtractor`）

### P0-2 数据一致性 MySQL ↔ Qdrant

- [x] 2a. 稠密检索不过滤 status/deleted，孤儿向量可被检索到。→ **已修**：检索尾部按 `documentId` 一次性反查 `kb_document`（`@TableLogic` 自动带 deleted=0 + status='READY'），丢弃孤儿向量切片，拉齐两路行为（`RetrievalServiceImpl.filterActiveDocuments`）
- [x] 2b. 删除时 Qdrant 失败被忽略，MySQL 已删而向量残留。→ **已修**：`cleanupChunksAndVectors` Qdrant 删除失败直接抛错（失败补偿路径外层 try/catch 已兜底），删除/重切/重试失败可感知可重试（`KnowledgeBaseServiceImpl`）

### P0-3 数据隔离与越权

- [x] 3a. 任意登录用户可删 / 重切 / 批量删全库文档。→ **已修**：`rechunk / retry / delete / batch-delete` 改为 `@SaCheckRole(value={"ADMIN","TEACHER"}, mode=OR)`（`KnowledgeBaseController`）
- [x] 3b. 旧 SSE 端点绕过 Redis 限流，匿名可检索全库。→ **已修**：`/ai/chat|rag|agent/stream` 通过 `rateLimited` helper 接入与 `/ai/stream` 同一全局队列限流，未获执行权回退"繁忙"提示（`AiChatController`）
- [x] 3c. 会话记忆跨用户串话：key 无 userId，空 conversationId 共享 default。→ **已修**：新增 `RagentContext.userScope()`（登录→`u{userId}`，匿名→`anon`），`ChatMemoryServiceImpl` 与 `MemorySummaryServiceImpl` 的存储键都加用户作用域前缀（`ChatMemoryServiceImpl.key`、`MemorySummaryServiceImpl.scopedConvId`）。注：升级后旧无作用域键自然过期；登录态变化会得到全新记忆

### P0-4 稳定性与线程模型

- [x] 4a. Netty 事件循环被阻塞：admitted 路径同步跑意图 LLM + 检索 + rerank。→ **已修**：`/ai/stream` admitted/queued 与旧端点全部改为 `Flux.defer(engine).subscribeOn(boundedElastic)`，阻塞管线移出事件循环（`UnifiedChatServiceImpl`、`AiChatController.rateLimited`）
- [x] 4b. 同步 `.call()` 无超时：Agent / 改写 / 摘要 / 评测可能挂死占线程。→ **已修**：`ChatModelRouter.call` 用有界池 + `Future.get(syncTimeoutMs)`（默认 30s），超时抛错进入候选降级；新增 `ragent.model.sync-timeout-ms` 配置（`ChatModelRouter`、`ModelFailoverProperties`）
- [x] 4c. 限流 inFlight 误减 + 断连泄漏。→ **已修**：`RELEASE_ADVANCE_LUA` 改状态感知——仅 admitted 才 DECR，queued/rejected/缺失只摘出 ZSET 不 DECR；请求键 TTL 60s→600s 杜绝长任务 release 漏判（`RedisRateLimiter`）
- [x] 4d. 熔断器 fallback 成功把失败端点 recordSuccess。→ **已修**：`tryStream` 的 `doOnComplete(recordSuccess)` 移到 `onErrorResume` 之前，成功只记在真正成功的端点链上（`ChatModelRouter`）

## 数据遗留问题（2026-08-05 核实并已清理）

**早期误判修正**：曾按"同名计数"（含逻辑删除行）判定存在 129 个重复文档。核实后确认——**活跃数据（deleted=0）本就没有同名重复**，那些"重复"是**逻辑删除的历史残留**（重复上传/删除时旧文档被应用置 deleted=1，`@TableLogic` 下不可见），属正常累积而非数据损坏。
- 已**实际执行清理**（先备份 `backups/ragent_before_dedup.sql`）：物理删除 135 条 deleted=1 的死行。
- 清理后三方完全一致：**46 文档 / 869 切片 / Qdrant 869 向量，0 同名重复、0 孤儿**。
- 代码侧已**加固**：`findLatestByFilename` 用 `selectOne + LIMIT 1` 取最新一条，即便将来出现同名多行，`selectOne` 也不会抛 `TooManyResultsException` 导致上传失败。
- 清理脚本 `backend/sql/p8_dedup.sql` 已更新为幂等的"清逻辑删除残留"版本。
